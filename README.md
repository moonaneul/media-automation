# 하늘빛기쁨성서침례교회 미디어 자동화

하늘빛기쁨성서침례교회의 주간 예배 자료 제작 업무를 자동화하기 위한 프로젝트입니다.

현재 미디어팀은 매주 다음 자료를 제작합니다.

- 수요예배 PPT
- 금요기도회 PPT
- 주일예배 PPT
- 주일 주보

이 프로젝트의 목표는 단순히 PPT 제작 시간을 줄이는 것이 아니라,

> 목사님·찬양리더 등 정보 제공자가 필요한 내용을 입력하면 시스템이 예배 자료를 생성하고, 미디어팀은 제작보다 최종 검수에 집중하는 구조

를 만드는 것입니다.

---

## 목표

최종적으로 다음과 같은 흐름을 지향합니다.

```text
목사님 / 찬양리더 / 담당자
        ↓
이번 주 예배 정보 입력
        ↓
구조화된 Weekly Data
        ↓
제작 엔진
        ↓
수요 PPT
주일 PPT
주보 PDF
금요기도회 자료
        ↓
자동 검수
        ↓
미디어팀 최종 확인
```

사람의 검수를 완전히 제거하는 것이 목표는 아닙니다.

목표 수준은 다음과 같습니다.

```text
자동 생성
→ 자동 검수
→ 사람이 짧게 최종 확인
→ 실제 예배 사용
```

# 핵심 설계

## 1. Weekly Data

수요·주일·주보에서 필요한 정보를 구조화된 데이터로 관리합니다.

특히 입력값은 다음 상태를 구분합니다.

```text
UNSET = 아직 정보가 전달되지 않음
NONE  = 이번 주에는 해당 항목이 없음
VALUE = 이번 주 사용할 값이 있음
```

지난주 값을 자동으로 승계하지 않습니다.

세부 규칙은 `AGENTS.md`를 따릅니다.

---

## 2. 블록 기반 조립

과거 한 주의 PPT 전체를 복사하고 텍스트만 바꾸는 방식보다
필요한 블록을 순서대로 조립하는 방식을 사용합니다.

예:

```text
고정 예배 안내
→ 빈 화면
→ 찬양 원본 슬라이드
→ 빈 화면
→ 기도
→ 빈 화면
→ 성경 본문
→ 빈 화면
→ 설교 제목
→ ...
```

곡마다 악보 슬라이드 수가 다르고,
성경 본문 절 수도 매주 달라지므로
최종 PPT의 슬라이드 수는 고정하지 않습니다.

---

## 3. 찬양 자료

수요·주일·금요 대면 예배에서는
가사만 있는 PPT가 아니라 기존 악보 PPT를 사용하는 것을 원칙으로 합니다.

기본 우선순위:

```text
사용자가 직접 제공한 정상 악보 PPT
        ↓
검수된 교회 보관 자료
        ↓
정상적인 외부 악보 PPT
        ↓
자료 없음
```

자료가 없는 경우 비슷한 곡이나 가사 PPT를 임의로 만들어 대체하지 않습니다.

향후 검수된 자료를 재사용할 수 있도록
찬양 라이브러리를 구축할 수 있지만,
저장 위치와 관리 방식은 아직 확정하지 않았습니다.

---

## 4. 성경 본문

성경 본문은 개역개정을 기준으로 생성합니다.

수요·주일은 기본적으로:

```text
한 절 = 한 슬라이드
```

구조를 사용합니다.

본문 생성, 절 번호 검수, `세례 → 침례` 등의 상세 제작 규칙은 `AGENTS.md`를 따릅니다.

---

## 5. 주일 PPT와 주보의 공통 데이터

같은 주의 주일 PPT와 주보를 따로 입력하지 않고,
공통되는 정보는 동일한 Weekly Data를 사용하도록 설계합니다.

예:

- 날짜
- 본문
- 설교 제목
- 찬양
- 기도 담당자
- 봉헌기도 담당자
- 특송
- 교회 소식
- 오후예배 정보

이를 통해 PPT와 주보 사이의 불일치를 줄이는 것이 목표입니다.

# 자동 검수

자동 생성 후 가능한 범위에서 다음을 검사합니다.

예:

- 성경 본문 범위
- 절 번호 누락
- 절 번호 중복
- `세례 → 침례`
- 설교 제목
- 담당자
- 찬양 곡명
- 찬송가 번호
- 주요 순서 사이 빈 화면
- PPT / 주보 공통 데이터 일치
- 지난주 정보 잔존 여부
- 불필요한 외부 URL
- 불필요한 객체

단순 파일 생성 성공을 실제 예배 사용 가능 상태와 동일하게 판단하지 않습니다.

렌더링, PowerPoint 실제 열기, 미디어 실제 재생 등은 별도의 검수 단계입니다.

# 금요기도회

금요기도회는 현재 1차 구현 범위에서 뒤로 둡니다.

금요기도회는 다음 두 형태가 존재합니다.

```text
Zoom 비대면
금요 대면
```

두 형식은 단순히 영상과 악보만 바꾸는 관계가 아니라
찬양 수, 기도 배치, 예배 순서 자체가 다를 수 있습니다.

특히 Zoom PPT는 영상과 음원이 내장된 대용량 자료이므로
수요·주일·주보 생성 구조가 안정화된 뒤 별도로 다룹니다.

# 향후 웹앱

생성 엔진이 안정화된 이후
브라우저 기반의 미디어팀 전용 웹앱을 검토합니다.

예상 형태:

```text
media.hjbbc.or.kr
```

기존 교회 홈페이지 `hjbbc.or.kr`을 직접 크게 수정하기보다
별도 시스템으로 운영하는 방향을 우선 검토합니다.

예상 입력:

```text
목사님
- 본문
- 설교 제목
- 광고 / 교회 소식

찬양리더
- 찬양 목록

담당자
- 기도
- 봉헌기도
- 기타 담당 정보
```

웹 UI, 로그인, 권한 관리, 관리자 대시보드 등은
핵심 생성 엔진보다 먼저 구현하지 않습니다.

# 자료 관리

기존 OneDrive의 과거 미디어 자료 전체를 새 시스템으로 이전하는 것을 목표로 하지 않습니다.

기존 자료는 기존 위치에 두고,
새 시스템에는 필요한 자료만 점진적으로 등록하는 방향입니다.

예:

- 검수된 예배 템플릿
- 검수된 찬양 PPT
- 필요한 메타데이터

실제 교회 예배 자료나 개인정보가 포함된 파일은
GitHub 저장소에 무조건 업로드하지 않습니다.

# 저장소 원칙

GitHub에는 기본적으로 다음을 관리합니다.

```text
코드
테스트
문서
제작 규칙
데이터 스키마
샘플 구조
```

실제 성경 데이터, 예배 입력, 영상·음원, 원본 자료와 결과물도 저장소에 보관합니다.
영상·음원·Office 파일·ZIP은 Git LFS로 동기화합니다.
가상환경, 캐시, 임시 파일과 인증정보만 제외합니다.
다른 컴퓨터에서 이어서 작업하는 방법은 [작업 동기화 안내](docs/workspace_sync.md)를 참고하세요.

# 주일 PPT와 주보의 전달 주보 공통 입력

같은 주 전달 주보는 한 번만 등록합니다. `sunday.py bulletin`과
`bulletin.py start`는 모두 `input/bulletin/YYYYMMDD/transfer.hwp|hwpx|txt`를
사용합니다. 주일 PPT 쪽은 이 원본에서 필요한 텍스트를 읽고, 주보 PDF도
같은 원본과 같은 주간 데이터를 사용합니다.

```text
python sunday.py bulletin 2026-10-04 전달_주보.hwp
python sunday.py resume 2026-10-04
python bulletin.py status 2026-10-04
python bulletin.py number 2026-10-04 <확인된호수>  # 해당 주 호수가 확인된 경우에만
python bulletin.py complete 2026-10-04
```

수정된 전달 주보는 `--replace`를 명시해야 교체됩니다. 날짜가 다르면 원본
등록과 산출을 중단하며 기존 등록본은 유지합니다. 주일예배 안내에 명시된
값이 우선이고, PPT의 `교회 소식 있음` 표시는 전달 주보의 상세 광고로
보완됩니다. 주보 생성 전에 같은 주의 주일 데이터와 전달 주보를 자동
대조하여 오래된 주일 데이터가 있으면 `sunday.py resume`을 요청합니다.
주보 PDF에서는 검증된 주일 데이터를 다시 덮어쓰지 않습니다. 찬양 원문은
개별 악보 슬롯에 임의 배정하지 않으며, 주보 호수도 과거 번호에서 추정하지
않습니다.

다음 개발 항목은 실제 주간 자료에서 주일 PPT와 주보 PDF의 공통 항목 및
렌더링 QA를 더 자동화하는 것입니다. 현재도 최종 예배용 자료는 육안
검수가 필요합니다.

# 작업 규칙

모든 제작 및 개발 작업은 `AGENTS.md`를 기준으로 합니다.

**규칙이 충돌할 경우 `AGENTS.md`가 최우선입니다.**
