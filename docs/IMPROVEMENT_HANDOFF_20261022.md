## 0. 다음 작업 담당자를 위한 1분 요약

- **해결하는 실제 문제:** 수요·금요·주일 예배 PPT와 주일 주보를 매주 제작할 때 발생하는 반복작업, 최신 수정사항 누락, 지난주 내용 잔존, 악보/미디어 누락, 성경/담당자 오기, 주일 PPT와 주보 불일치.
- **현재 강점:** 실제 제작 경험 및 과거 출력 검수 이력, 예배 유형별 형식 보존, 주간 입력 `UNSET / NONE / VALUE`, 원본 보존, 누락 자산의 명시적 기록, 생성과 검수의 개념적 분리.
- **현재 핵심 약점:** 구현 경로/인프라가 복수로 존재하고, *최신 코드 + 최신 웹 UI + Mac 원본 + 실제 예배 환경* 전체 조합에서 담당자가 끝까지 사용하는 검증이 충분하지 않음. 신규 기능보다 **한 번의 완전한 사용자 제작 경험**을 우선.
- **개발 방향:** 기존 제작 엔진을 재작성하지 말고 정리·공유. 별도 디자인인 수요/금요/주일 PPT를 통일하지 않음. 클라우드 확대는 실제 팀 협업 요구와 독립 통합 검증 뒤로 미룸.
- **지금 해야 하는 다음 행동:** Windows ZIP 52개 파일을 Mac으로 옮기고 해시 검사 및 별도 스테이징, **Mac 실사용 DB/원본/미커밋 코드 확인** 후 보존형 통합. Windows 원본 삭제는 최종 검증 뒤.

## 2. 무엇을 성공으로 볼 것인가 — 제품 목표

**최종 사용자 경험:** 담당자가 이번 주 안내를 전달받아 웹에서 수요/금요/주일 PPT 또는 주보를 선택하고, 안내·수정지시를 확인하고, 필요한 원본을 연결하고, 오류를 확인해 수정하고, 실제 화면·재생·인쇄를 검수한 뒤 **예배에 사용할 최종 결과물을 승인·내보내는 것**.

다음을 별도로 판정한다.

1. **입력 준비:** 해당 주 최신 안내와 수정 지시가 반영되고 필수 값/원본이 확인됨.
2. **생성:** 코드가 PPTX/PDF를 생성했고 구조 검사·신규 산출물 검출을 통과함.
3. **검수:** 실제 화면, 내용, 미디어 재생/인쇄를 사람이 확인함.
4. **사용 승인:** 검수 담당자와 승인 시각, 대상 파일 해시를 기록함.
5. **운영:** 다른 담당자도 개발자의 터미널 개입 없이 반복 가능하고 장애 시 수동 대안이 있음.

**금지:** '파일 생성 성공', '테스트 N개 통과', 'Cloud Run 배포 성공'을 곧바로 예배 사용 승인이라고 부르지 않는다.

## 4. 가장 먼저 실행할 일: Windows → Mac 이전

**이미 완료된 Windows 작업:** 최신 검수 코드 `cb8176e` 반영, 전송 ZIP 52개 생성 및 동일 해시 검증, 바탕화면에 `device_transfer.py` 복사. **Mac 반영은 아직 미완료.**

1. Windows 바탕화면의 `media-automation-win-inputs-20261022.zip`, `device_transfer.py`를 Mac `~/Downloads/`로 안전하게 전송한다.
2. Mac **기존 폴더를 건드리기 전에** `ls -d ~/Documents/media-automation*`, `git -C ~/Documents/media-automation status --short --branch`, `git -C ~/Documents/media-automation log -1 --oneline` 결과를 확인한다. Mac 로컬 `output/main-database.txt`, 실제 DB, `work.files` 등 참조 원본을 **별도로 점검**한다.
3. Mac에서 다음 절차로 ZIP의 내용·해시 확인 후 기존 프로젝트와 다른 staging에만 복사한다.

```bash
python3 ~/Downloads/device_transfer.py verify \
  --bundle ~/Downloads/media-automation-win-inputs-20261022.zip

mkdir -p ~/Documents/media-automation-win-staging-20261022

python3 ~/Downloads/device_transfer.py import \
  --bundle ~/Downloads/media-automation-win-inputs-20261022.zip \
  --destination ~/Documents/media-automation-win-staging-20261022

python3 ~/Downloads/device_transfer.py import \
  --bundle ~/Downloads/media-automation-win-inputs-20261022.zip \
  --destination ~/Documents/media-automation-win-staging-20261022 --copy

python3 ~/Downloads/device_transfer.py import \
  --bundle ~/Downloads/media-automation-win-inputs-20261022.zip \
  --destination ~/Documents/media-automation-win-staging-20261022
```

4. **최종 staging 검증:** `copy_candidates=0`, `conflicts=0`, `identical_files=52`, ZIP SHA-256 위 값 일치. 이 결과는 *전송 보존* 검증이지 실사용 프로젝트 복구 완료는 아니다.
5. Mac 코드·DB·고유 파일과의 차이를 점검한 뒤 어느 checkout이 실제 제작 기준인지 결정한다. 서로 다른 작업 DB를 자동 덮어쓰기/병합하지 않는다. GitHub 코드만 먼저 써 보고 싶다면 **별도 checkout**에서 시험한다. 기존 제작용 `start.command`/DB는 검증 전 유지.
6. Mac의 선정된 활성 프로젝트에서 원본 경로·기존 입력·폰트·Office 연동·성경 조회·실제 제작/열기·필요한 로컬 로그인 재설정을 시험한다. **중요 원본은 Windows 이외의 독립 백업도 보유**한 뒤 Windows 정리를 시작한다.
7. 위가 확인되면 Windows `Documents/media-automation` 및 `Documents/media-automation-archive-20261022`의 **정확한 절대경로**를 다시 확인하고 `Remove-Item -WhatIf`로 대상 미리보기를 검토한 후에만 삭제한다. 지금 즉시 삭제하지 않는다. PC를 제3자에게 넘기는 경우 프로젝트 폴더 제거와 별도로 사용자 계정/OS 초기화 계획을 세운다.

**이관 대상에서 제외하기로 사용자 확인한 것:** 오래된 `output/` PPT, 잔여 0.47GB의 영상·음원·검수 출력, 오래된 Windows archive의 기타 자료. **다만 Mac에 이미 존재하는 고유 실사용 DB/원본 및 별도 악보 원본 라이브러리는 동일하게 삭제 대상이 아니다.**

세부 절차: [Windows → Mac 이전](windows_to_mac_transfer_20261022.md), [멀티디바이스 구분](multi_device_workflow_20261022.md).

## 5. 실제 예배 운영이 우선인 개발 순서

### Phase A — Mac 활성 환경 확인, 현업 제작 지속

- [ ] 현재 사용 중인 Mac 서버·실사용 프로젝트·DB 경로를 확인하고 스냅샷/복구 경로 확보.
- [ ] Windows ZIP의 해시/개수 검증, staging 보존 후 Mac 실사용 고유 자료와 비교.
- [ ] 코드 한 갈래를 **향후 개발 기준**으로 선택하되 기존 제작 경로를 삭제/중단하지 않음.
- [ ] Mac 테스트 환경에서 Python 패키지/필수 폰트/PowerPoint/LibreOffice/영상 환경 확인.
- [ ] 실사용 DB를 새 빈 DB로 조용히 대체하지 않고 동일 자료·참조파일이 유지되는지 확인.
- [ ] Windows 로컬 폴더 삭제는 위 항목 확인 후에만.

### Phase B — 수요예배 1회 완전한 웹 제작

수요를 첫 실사용 시나리오로 추천하는 이유: 4:3, 악보 원본·절별 말씀·빈 화면·단독 중앙 정렬 등 핵심 공통 규칙을 포괄하면서 Zoom 미디어/주보 접지의 추가 변수를 피할 수 있기 때문.

- [ ] 해당 주 원문 안내와 이후 수정사항을 순서대로 입력. 임의로 지난주 담당자/찬양을 채우지 않음.
- [ ] 화면에서 각 필드의 현재 값·출처·확정/미확정 상태를 **한국어로** 확인/수정.
- [ ] 필요한 악보 원본·성경 JSON·예배 전 화면을 파일/곡명 기준으로 연결.
- [ ] 필수 항목/본문/악보 누락에 대해 실패 이유가 구체적이고 복구 방법이 보이는지 검증.
- [ ] 실제 PPT 생성 후 구조 QA, **전체 슬라이드 렌더링** 및 원본 악보·본문 육안 점검.
- [ ] 검수 결과와 최종 승인 상태를 남기고 **승인 대상 해시와 다운로드 파일을 연결**.
- [ ] 제작 담당자가 터미널이나 직접 YAML 편집 없이 위 흐름을 진행할 수 있는지 관찰.

**수요 DoD:** 실제 예배에서 쓸 수 있는 1개 주차가 최신 웹 흐름으로 제작되고, critical 내용 오류 0건, 누락·임시 화면의 최종 승인 차단, 최종 PPT가 운영 PowerPoint에서 정상 표시되며, 사람이 승인 증거를 확인 가능. 기존 제작과 소요 시간/수정 건수를 비교 기록.

## 6. 보존해야 할 교회 제작 정책 (회귀 방지)

1. **현재 주차의 최신 안내 우선.** 최초 안내에 수정 지시를 누적하되 같은 필드는 가장 최근의 명시적 지시를 사용한다. 안 바뀐 필드만 유지. `UNSET`(미제공)과 `NONE`(명시적 빈칸/없음)을 구분.
2. 이전 주의 날짜·담당자·곡·본문·찬송가 번호·광고·기도·목장 질문 등을 **자동 승계하거나 순번 추정하지 않는다**.
3. 성경은 **개역개정**, 화면에서는 원문에 `세례`가 있을 때 `침례`로 변경. 실제 절 범위·번호·중복/누락·이미지 속 본문까지 검수.
4. **수요/주일:** 한 절당 한 화면이 기본. **금요 Zoom:** 분량에 따라 여러 절 가능. 새 4:3 본문 글꼴은 보통 30~34pt, 범위 표기는 26~30pt에서 시작해 렌더를 보고 조정, 줄간격은 대략 1.4~1.5.
5. 기도·설교 제목 등 단독 화면은 가로·세로 중앙 정렬. 신규 텍스트 화면은 기본 흰 배경/검정 글씨이며 파란 사각형 배경을 넣지 않음. **기존 찬양 PPT 디자인은 임의 변경 금지**.
6. 수요 등의 주요 순서 변경 경계에 **빈 슬라이드 1장**. 절마다 빈 슬라이드를 넣는 것이 아님.
7. 수요·주일·금요 **대면**은 정상 악보 PPT 원본 사용, 가사만으로 대체 금지. 사용자가 준 악보 사진을 잘라 확대·분할해 예배 악보로 쓰지 않음. 정상 악보 없으면 해당 위치는 **빈 화면**(제작자용 '미삽입' 텍스트도 화면에 노출 금지). 별도 검수 보고서에는 누락을 명시.
8. 금요 Zoom은 찬양 영상/음원. **재생 파일 존재 ≠ 실제 재생 성공**. 금요 대면 여부는 자동 계산하지 않고 사용자 명시. 기존 대면과 Zoom 순서는 별도로 보존.
9. 저작물 파일 보유/인터넷 검색 성공 ≠ 교회의 사용 허락. 허락 상태를 별도 확인하고 기록.
10. 주보는 A4 양면 한 장의 접지본 PDF가 기본. **PDF 1페이지 [4쪽,1쪽], PDF 2페이지 [2쪽,3쪽]**, 실제 크기 100%, 양면 짧은 쪽 넘김. 이미 배치된 PDF를 '소책자 인쇄'로 중복 재배치 금지.
11. `sources/` 원본 자료는 읽기 전용으로 다루고 결과는 별도 경로로 생성. 주일 PPT/주보는 **같은 주** 공통 정보 교차검수.
12. 미디어/성경/악보의 정답성을 파일명·자동 추출 텍스트만으로 가정하지 말고 실제 렌더와 재생 검수를 기록.

## 7. 테스트 우선 순위: 반복 실행 가능한 품질 기준

**자동 게이트** (입력/구조):
- 누락 vs 빈 값 vs 명시 값, 동일 주차의 연속 수정 2회 이상, 충돌 출처.
- 이번 주 변경 없는 필드 유지, 다른 주 데이터의 잔존 금지, 날짜/담당자 불일치.
- 같은 주 주일 PPT/주보 본문·설교·담당자 대조, 질문 원문 4개 보존.
- 개역개정 절 범위/절 번호/중복/누락/침례 치환.
- 찬양 원본의 정확한 슬롯·곡명·번호·절·후렴 여부(검증 가능한 영역), 누락 시 잘못된 대체 없음.
- 4:3/16:9·빈 경계 화면·중앙 정렬·슬라이드 누락·예배와 무관한 링크 유입·PPT 패키지 무결성.
- ZIP/DB/원본 덮어쓰기 방지, 취소/재시도/동시 수정 충돌, 산출물 해시.
- 자동 테스트의 Mock/합성 사용 여부 표시. 실제 원문/운영 재생을 테스트했다는 과장 금지.

**사람 게이트** (반드시 별도):
- PPT 전장 렌더, 말씀 이미지/악보 이미지 속 텍스트, 제목·절 번호·줄바꿈·여백.
- Zoom MP4/MP3를 예배에 사용할 **PowerPoint 및 실제 출력 환경**에서 열고 재생.
- 주보 두 인쇄면 렌더 + **실제 A4 양면 인쇄·접지**.
- 마지막 주간 안내와 완성본 대조, 사용 허락 확인, 최종 승인자 기록.

**버그 판정:** 예배 화면에 잘못된 성경 본문, 지난주 정보, 다른 찬양이 출력되거나 승인되지 않은 초안이 최종본으로 표시되면 P0 회귀 버그. 예배 임박 시 새 기능 개발보다 수동 제작·복구 경로 확보가 우선.

## 9. 서비스 평가와 리스크 결정 기록

**종합 판단:** 기술적 기반과 실제 예배 제작 경험은 존재하나, 지금은 기능의 개수를 늘리는 것보다 **실사용 가능한 end-to-end 품질, 사용자 이해도, 운영 복구 가능성**을 강화할 시점.

**유지할 결정:** `UNSET/NONE/VALUE`, 과거 주차 자동 승계 금지, 예배별 차별화된 디자인, 악보 원본 보존, 누락 시 조용한 타 곡 대체 금지, 자동 생성과 최종 검수 분리, 입력/산출물의 해시와 출처 기록.

**고쳐야 할 결정:** 개발자가 여러 API·YAML·폴더를 알고 있어야만 작업이 진행되는 경험; 작업 완료와 검수 승인 상태 혼동; 서로 다른 앱 코드 경로의 정책 중복; 운영 요구 검증 전 클라우드 인프라 확대; 성능을 PPT 생성 시간만으로 평가하는 방식.

**현재 보류:** 별도 찬양 라이브러리의 저장 장소/시스템 확정, 새 관리자 포털, 자동 운영 배포, 실교회 원본을 이용한 비승인 원격 테스트.

## 10. 실제 효과 측정 및 사용자 관찰

**기준선:** 수동 방식과 현재 서비스 모두에서 예배 유형별로 '안내 수신 → 자료 확보 → 입력/수정 → PPT/PDF 생성 → 전장 검수 → 수정 → 최종 공유'의 전체 시간을 기록한다.

최소 측정 필드: 예배 유형/주차(민감 세부 제외), 원본 확보 시간, 안내 정리 시간, 제작 실행 시간, 검수 시간, 수정 횟수, 누락/오류 유형, 자동 차단 발견 건수, 사람 수동 개입 횟수, 최종 승인 여부. 숫자는 **실측 전에는 추정치로 대체하지 않는다**.

사용성 검사: 제작을 익히지 않은 미디어팀원 1인이 개발자의 터미널/코드 수정 없이 새 주차를 준비한다. 막히는 지점을 기록하고 UI를 수정한 뒤 같은 과정을 재시험한다.

## 11. 다음 채팅/개발자에게 전달할 즉시 실행 지시

> 현재 실제 교회 예배용 PPT를 제작하는 업무가 계속 진행 중이다. 서비스 수정으로 현업 경로를 멈추거나 과거 원본/DB를 삭제하지 말 것. 첫 작업은 Windows에서 검증된 52개 파일 ZIP을 Mac의 별도 staging으로 해시 검증하고, 기존 Mac `media-automation`의 Git 상태·실사용 DB·고유 자료/실행 경로와 비교하는 것이다. Mac 이전 검증 전에 Windows 프로젝트 폴더를 삭제하지 않는다. 이후 기존 작동 코드 위에서 **수요예배 1회 전체 웹 제작→검수→승인** 과정을 완성하고, 금요 Zoom·금요 대면·주일 PPT·주보로 확장한다. 클라우드 새 배포보다 로컬 실사용의 정확성과 복구를 우선한다. 작업마다 변경 범위·근거·테스트·실제 렌더/재생 검수 여부·미완료를 구분해 보고하고, 실제 자료에 접근할 수 없으면 검사했다고 말하지 않는다.
