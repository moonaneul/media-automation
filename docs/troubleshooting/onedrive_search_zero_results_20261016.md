# 트러블슈팅: OneDrive에 악보가 있는데 예배 화면에서는 0건

**일자:** 2026-10-15~16 / **범위:** 로컬 검수 서버 18877 / **해결 검증:** 사용자 실제 검색·PPT 악보 삽입 성공

## 증상과 초기 오해

- 사용자의 OneDrive 악보 PPT 원본 폴더에서 135장.PPT 파일 존재를 확인했으나 예배 화면의 135장 검색은 0건.
- 380장 검색도 0건이었음. 다만 380장 파일의 동일 위치 실존 여부는 이 진단에서 확인하지 않았다.
- Microsoft Graph 검색 색인/계정/폴더 설정을 먼저 의심했지만 **실제 원인은 브라우저 쪽 필터**였다.

## 재현과 단계별 범위 축소

1. 브라우저에서 OneDrive 파일 목록에 135장.PPT 확인.
2. 동일 검수 서버의 GET /api/onedrive/files?purpose=source&q=135장 결과 HTTP 200, 검색 파일 **1개**.
3. 같은 purpose를 검색어 없이 조회하면 HTTP 200, 파일 **114개**, 135 포함 이름 1개.
4. 브라우저의 CloudMedia.searchWorshipSource('135장','score') 실행 결과는 status=ok, items=[].
5. 원시 응답의 135장.PPT는 source_role=score, 파일 인식 true, 정상 확장자 정규식 통과 true.
6. 실제 실행 중인 함수 문자열을 확인해 확장자 정규식에 잘못된 역슬래시가 사용된 것을 발견.

## 근본 원인

브라우저에서 실행 중이던 구형 JS의 확장자 필터:

    /\\.pptx?$/i.test(name)

올바른 확장자 필터:

    /\.pptx?$/i.test(name)

앞의 식은 정상적인 PPT 확장자를 판별하지 못한다. MP4·MP3에 사용된 같은 패턴도 영향 범위였다.

GitHub 개발 브랜치에는 이미 수정 코드가 올라가 있었지만, **로컬 검수 서버가 이전 코드를 실행 중이었기 때문에 수정 효과가 화면에 반영되지 않았다.** 즉 서버 검색 API의 0건 문제가 아니었다.

## 해결·실제 검증

- 개발 브랜치 fix/ui-workflow-20261015의 정규식 수정 상태 확인.
- 검수 서버 18877만 재시작하고 해당 개발 브랜치 버전으로 갱신; 브라우저 강력 새로고침.
- 사용자 실제 화면에서 135장.PPT 검색 성공.
- 사용자가 이 OneDrive 원본을 선택한 뒤 **실제 예배 PPT에 악보가 삽입된 것**까지 확인.
- 이 확인은 다른 곡, Zoom 영상 재생, 완료본 OneDrive 보관의 성공을 의미하지 않는다.

## 재발 방지

- JS 런타임 자체를 실행하는 검색 회귀 테스트에서 대문자 PPT, PPTX, MP4, MP3를 검사한다.
- 문제 위치를 API 응답 → 프론트 필터 → 화면 표시 → 다운로드·PPT 삽입으로 나누어 확인한다.
- 코드 배포/서버 재시작 후 실제 브라우저가 실행하는 버전 확인; 개발 브랜치에 코드가 존재한다는 사실만으로 해결 완료라고 판단하지 않는다.
- 검색 화면에 별도의 디버그 UI를 계속 추가하지 않는다. 사용자 화면은 곡명·번호 검색 → 결과 선택으로 간단히 유지한다.
