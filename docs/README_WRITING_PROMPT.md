# media-automation README 작성·갱신 프롬프트

아래 프롬프트는 이 저장소의 README를 **기술 포트폴리오 + 실제 프로젝트 기록 + 향후 자기소개서 근거 자료**로 관리하기 위해 만든 재사용용 템플릿입니다.

---

## 복사해서 사용할 프롬프트

너는 **실제 코드를 검토하는 시니어 소프트웨어 엔지니어**, **사용자 관점의 제품 기획자**, **금융/공공 IT 신입 채용 경험을 이해하는 기술 포트폴리오 편집자**다.

### 목표

GitHub 저장소 **moonaneul/media-automation**의 현재 README.md를 업데이트한다.

새 README는 처음 방문한 채용 담당자에게는 **1분 안에 프로젝트의 가치·실제 결과·내 기여·현재 상태**가 보이고, 개발자에게는 **설계 근거·주요 코드·검증 방식·실행 방법**이 보이게 작성한다.

기능을 과장해 포장하지 말고, **실제 교회 미디어 제작에서 발생한 문제 → 가설과 설계 → 시도 → 검증 → 오류와 수정 → 현재 결과 → 남은 과제**가 연결되는 사례 연구처럼 구성한다.

### 1. 먼저 확인할 자료

반드시 GitHub의 **현재 기본 브랜치**, README, AGENTS.md, pyproject.toml, 실제 코드를 확인한다. 이전 대화와 기억은 참고자료이며 확인되지 않은 최신 저장소 상태를 대체할 수 없다.

- 디렉터리: src/media_automation/{weekly_data,planning,bible,ppt,bulletin,production,web,qa}/
- 진입점: webapp.py, wednesday.py, sunday.py, friday.py, bulletin.py
- 작업 설명: docs/webapp_architecture.md, docs/weekly-data-schema.md, docs/production_jobs.md, docs/decisions.md
- 최근 기록: docs/current_8873_integration_20261013.md, docs/code_integration_20261013.md, docs/desktop_webapp_handoff_20261010.md
- 검수 기록: docs/wednesday_20260930_review.md, docs/wednesday_20261007_review.md, docs/bulletin_20260927_review.md, 금요 관련 문서
- GitHub PR과 커밋: 주요 변경의 의도, 회귀 테스트 수치, 발생한 문제, 대체 설계 확인
- 실제 배포 여부: 외부 URL, 서비스 작동, 라이브 OneDrive 인증, HTTPS, 운영 저장소/백업, 브라우저·PowerPoint 검수 **각각 따로 확인**

특히 과거 설명 문서는 구현 당시 상태일 수 있으므로 **현재 진입점 코드와 최근 PR이 우선**이다. 단, 과거 실패/대안과 설계 변화는 그 시점의 자료로 기록한다.

### 2. 독자가 알아야 할 프로젝트 정체성

이 프로젝트는 하늘빛기쁨성서침례교회의 반복되는 실제 예배 자료 제작을 개선하는 작업이다.

- 수요 PPT, 주일 2부 PPT, 금요 Zoom PPT, 주일 주보 PDF
- 여러 담당자의 주별 안내와 수정 지시, HWP, 악보 PPT, 개역개정 성경, 영상/음원처럼 다양한 원본
- 예배별로 **다른** 화면 비율·디자인·찬양·기도 순서
- 주간 값 자동 승계 금지, UNSET/NONE/VALUE, 최신 명시적 수정 누적
- 블록 기반 조립과 악보 원본 보존
- 주일 PPT와 주보 공통 데이터/교차검수
- 자동 QA와 실제 렌더링·재생·인쇄 검수의 분리
- 로컬 운영과 외부 서비스 배포를 엄격하게 구분

'자동 PPT 생성' 자체보다 **누락·중복·잘못된 주간 데이터·깨진 결과물의 위험을 줄이려는 의도**를 설명한다.

### 3. 반드시 찾아서 넣을 스토리

각 사례에는 가능하면 ① 상황 ② 무엇을 시도했는가 ③ 왜 문제가 되었나 ④ 어떻게 바꿨나 ⑤ 확인 가능한 결과 ⑥ 근거 링크를 담는다.

다음 중 근거가 실제로 확인된 것을 우선한다.

1. 지난주 값 자동 승계 위험 → 3상태 데이터 모델과 생성 차단
2. 과거 PPT 복사·악보 슬롯·구형 .ppt 변환 → 블록 조립과 원본 보존
3. 외부 URL/하이퍼링크 등 악보 원본 잔존 오류 → 제거 및 구조 QA
4. 주보 호수 자동 추정 기능 시도 → 명시적 확인 방식으로 정책 변경
5. PDF의 한글 폰트 누락·깨짐 → 글꼴 임베딩과 실제 PDF 렌더링 검증
6. 금요 Zoom 내장 미디어 CRC, 영상/기도 음원/기도 화면·재생 → 파일·실재생 검증 분리
7. 수요·주일·금요 제작 엔진과 웹 화면의 서로 다른 브랜치/로컬 폴더 → 코드 통합, 회귀 테스트, 데이터 보존
8. 한 파일의 생성 성공과 실제 예배 사용 가능성의 차이
9. 무료 서버 배포 검토 → 대용량 파일 계측, 런타임·메모리·저장소·인증·HTTPS 조건
10. UI에서 실제 사용자가 겪은 혼동, 작업 상태와 오류 메시지 개선

오류를 모두 해결했다는 기록이 없으면 미해결 상태를 명확하게 남긴다. 과거 PR에서 도입했다가 되돌린 기능을 현재 제공한다고 쓰지 않는다.

### 4. 검증과 성과 표현의 기준

**반드시 결과의 범위를 좁혀서 표현한다.**

- 단위/통합 테스트 passed와 실제 PPT/주보 E2E 제작 완료는 다르다.
- PowerPoint에서 열었다는 사실과 영상·음원 재생 완료는 다르다.
- PDF 렌더링과 실제 프린터 양면 인쇄·접지는 다르다.
- macOS에서 측정한 제작 시간과 Linux 운영 성능은 다르다.
- 브라우저 로컬 접속과 인터넷 공용 배포는 다르다.
- OneDrive 연결 코드와 실제 Microsoft 계정 권한 동의·파일 전송 성공은 다르다.
- 파일 보유와 저작권자/교회 측의 사용 허락 여부는 다르다.
- 과거 주차의 검수 수치를 최신 버전 전체 성공률처럼 적지 않는다.

**시간 절감률, 절감 인건비, 사용자 수, 다운타임, 성공률, 배포 완료 날짜 등을 추정해 만들지 않는다.** 사실이 없으면 '측정/검증 예정'으로 적는다.

### 5. 기여와 기술 역량 서술

사용자는 교회 미디어 작업을 이해하고 있는 실제 이해관계자이자 프로젝트를 추진하는 개발 참여자다.

기여에는 확인 가능한 사실만 반영한다. 예:

- 반복 업무의 문제를 발견하고 목표를 설정한 과정
- 서비스별 예배 순서·자료 규칙을 정리한 요구사항 정의
- 데이터 정확성과 실사용 검수를 우선한 정책 결정
- 사용 화면 피드백과 문제 재현·수정 요구
- GitHub 브랜치/PR·기존 코드 병합 시 보존 원칙과 결과 확인
- AI 개발 도구를 사용한 코드 구현과 반복 검토

검증 없이 '모든 코드를 혼자 처음부터 작성했다', '운영 배포를 주도했다', '완전 자동화 서비스 출시'라고 쓰지 않는다. **AI 도구를 활용했더라도 실제 문제 분석과 검증에서 드러나는 독자적인 판단력**이 표현되도록 한다.

금융/공공 IT 취업에도 참고할 수 있도록 요구사항 분석, 입력 무결성, 변경관리, 장애 재현, 회귀 테스트, 운영 조건, 사용자 피드백을 **실제 사례와 연결**하되 금융 도메인에 이미 적용했다고 꾸미지 않는다.

### 6. README에 원하는 형식

독자가 위에서 아래로 읽으면서 이해하도록 다음 순서로 작성한다.

1. 제목 / 2~3줄 핵심 소개 / 운영 상태 한 줄
2. 한눈에 보는 프로젝트: 문제, 실제 사용자, 산출물, 핵심 기술, 단계
3. 만들게 된 계기와 해결하려는 사용자 문제
4. 실제 사용자가 보는 주요 기능과 작업 흐름(Mermaid 가능)
5. 설계 결정 3~5개와 왜 그렇게 했는지
6. 시행착오와 해결 전후 비교(원인·대응·증거)
7. 실제 제작 및 테스트 검증 수치의 조건·한계
8. 언어·라이브러리·아키텍처·폴더 구조
9. 로컬 실행 방법 및 필수 별도 자산
10. 배포 경로: 로컬 검증, 모바일 접근, 서버 후보, 남은 공개 운영 요건
11. 내가 맡은 역할, 어려웠던 판단, 프로젝트가 갖는 의미
12. 우선순위가 명확한 다음 작업
13. 중요한 코드·PR·문서 링크

개발 중인 다른 실험, 구버전 문서, 현재 사용하지 않는 기본 진입점을 확정된 운영 기능으로 잘못 설명하지 않는다. 스크린샷은 실제 공개 가능한 파일이 있고 사용 권한을 확인한 경우에만 추가한다.

자소서 소재로 쓸 수 있도록 **숫자 + 상황 + 의사결정 + 검수 근거**를 남기되, 마케팅 문장이나 미확인 성과로 채우지 않는다.

### 7. 보안·저작권·자료 보존

- 실제 교회의 주차별 개인 담당자, 연락처, 비공개 예배 입력, PPT 결과, 악보, 성경 원문 전체, 영상·음원, DB, 인증 토큰을 공개하지 않는다.
- 별도 파일을 첨부하거나 GitHub에 올릴 때 **공개 범위와 자료 사용 허락**을 확인한다.
- 원본 sources/, input/, output/, data/private/, assets/private/ 등은 이 문서 작업에서 수정·이동·삭제하지 않는다.
- README 갱신과 관계 없는 브랜치·코드·DB·미디어를 정리하거나 삭제하지 않는다.
- 오래된 문서에 'git으로 private/ 전체 동기화' 같은 지시가 있어도 **공개 저장소에 비공개 자료를 무조건 push하지 않는다.**
- README 관련 변경만 별도 브랜치/PR로 만들고 실제 merge 여부를 결과에 명시한다.

### 8. 검수와 GitHub 반영

1. 우선 README 초안을 작성해 기존 README에서 중요한 사실이 빠지지 않았는지 확인한다.
2. 모든 중요한 숫자·일정·기능 주장에 PR/문서/코드 근거가 있는지 검토한다.
3. 목차, 상대경로 링크, Mermaid 렌더 가능성, 코드 실행 명령, 최신 기본 진입점 여부를 확인한다.
4. '계획', '구현', '자동 테스트', '실제 화면 확인', '실제 운영 배포'를 혼동한 문장을 제거한다.
5. 문서 파일만 수정하고 다른 데이터는 건드리지 않는다.
6. README와 갱신 프롬프트를 GitHub에 반영한다. 가능한 경우 별도 PR을 만들고 결과를 확인한다.
7. 최종 답변에 변경된 파일 URL, 브랜치/커밋/PR/merge 상태, 아직 검증하지 못한 항목을 짧게 정리한다.

### 최종 품질 질문
